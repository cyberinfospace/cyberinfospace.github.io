# Cyber Info Space — 2027 Website Redesign

> **Design specification and creative direction**  
> Version: 1.0  
> Prepared: 12 November 2026  
> Project: Cyber Info Space (CIS) — corporate website redesign  
> Design direction: Premium hybrid (light editorial + dark technology sections)  
> Primary deliverable: High-fidelity responsive website design specification

---

## 0. Executive summary

Cyber Info Space should evolve from a GitHub-oriented project index into a credible, product-minded technology engineering brand. The redesigned website must communicate that CIS works across software surfaces—mobile, web, desktop and AI—while retaining the openness and practical engineering character of its GitHub roots.

The proposed experience combines:

- A **light, editorial introduction** that feels clear, confident and approachable.
- A **distinctive hero visual** built around a refined orbital / connected-systems artwork.
- A compact capability system covering mobile applications, web platforms, desktop software, AI and agentic systems, and research / open source.
- A **dark AI and systems section** that creates a memorable visual contrast and explains the company's direction without relying on exaggerated AI claims.
- A selected-work area that gives real projects the attention they deserve.
- Clear paths to GitHub, the main website, project details and direct contact.
- A mobile experience designed as a first-class layout, not a compressed desktop page.

The target impression is **an ambitious, capable independent technology company**: polished enough to work with serious clients and collaborators, while honest about its actual portfolio, size, track record and maturity.

### The central message

**Engineering what's next.**

Supporting statement:

> We build digital products, intelligent software and autonomous systems—from idea to impact.

Alternative hero headline used in the visual concept:

> We build what moves technology forward.

Use one primary headline consistently across the live site. The alternative can be retained for campaigns or tested later.

## 1. Project context and current-state observations

### 1.1 Current site

Reference: [https://cyberinfospace.github.io/](https://cyberinfospace.github.io/)

The crawler-visible version of the existing site presents CIS as an **Official GitHub Index**. It includes the CIS name, links to the main website and GitHub, the line **“AI • ML • Cloud • Cybersecurity”**, a project directory, project search/filter controls and an open-source/project-discovery message.

The captured page also displays a loading/project-empty state. This should be treated as a state to investigate, not proof that the GitHub organisation has no public repositories. Confirm the source of the project feed, API permissions, response handling and browser-console errors before launch.

### 1.2 What should be retained

- The Cyber Info Space / CIS identity.
- The relationship to the GitHub organisation and public repositories.
- The idea of a central place to discover projects, tools and engineering work.
- The technology breadth already implied by AI, ML, cloud and cybersecurity.
- Direct routes to the main website and GitHub profile.

### 1.3 What should change

- Move from a directory-first layout to a **company story and capability-first experience**.
- Replace generic technology labels with clear descriptions of what CIS designs and builds.
- Give real products and projects a deliberate presentation system.
- Explain AI and agentic systems through understandable workflows and use cases.
- Establish a consistent visual language rather than relying on a basic index-page treatment.
- Make contact and collaboration routes obvious.
- Treat mobile navigation, reading order, cards and artwork as deliberate design decisions.

### 1.4 What this design does not assume

No unverified claims should be introduced to make the company look larger. The design does not assume a particular founding year, employee count, client roster, office location, revenue, awards, certifications, deployment scale or number of shipped products. Add these only when the company can substantiate them.

## 2. Brand strategy and positioning

### 2.1 Recommended positioning

**Cyber Info Space is an independent technology engineering company building digital products, software platforms and intelligent systems.**

This positioning is broad enough to cover the intended portfolio, but specific enough to avoid presenting CIS as a vague “everything technology” agency.

### 2.2 Brand promise

**From ideas to useful technology.**

CIS connects product thinking, software engineering and applied intelligence to create useful digital experiences across devices and platforms.

### 2.3 Brand personality

| Attribute | How it should feel | What to avoid |
|---|---|---|
| Intelligent | Thoughtful, precise, technically fluent | Dense jargon and unnecessary complexity |
| Ambitious | Forward-looking and inventive | Unsupported “world-leading” claims |
| Practical | Product-led, useful and shippable | Abstract innovation language with no examples |
| Independent | Curious, self-directed, open to collaboration | Pretending to be a large corporate group |
| Trustworthy | Clear, transparent and consistent | Fake client logos, inflated numbers or invented testimonials |

### 2.4 Audience groups

1. **Potential clients and product owners** — want to understand what CIS can build, how it works and how to start a conversation.
2. **Technical collaborators** — want to evaluate engineering interests, technical areas and project quality.
3. **Developers and open-source users** — want to find repositories, documentation, releases and contribution paths.
4. **Potential team members** — want to understand the company's technical direction and working principles.
5. **Curious visitors** — need a quick, clear explanation of what Cyber Info Space is.

### 2.5 Primary user journeys

- **Discover CIS:** Hero → capabilities → selected work → about → contact.
- **Evaluate a service:** Capabilities → relevant work → delivery approach → contact.
- **Explore a project:** Selected work → project detail / live demo / repository.
- **Find open-source work:** Open source section → GitHub organisation → repository.
- **Start a collaboration:** Header CTA or contact section → contact method / enquiry form.

The site should always make these journeys possible without requiring users to scroll to the footer to find the next step.

## 3. Creative direction: “Connected intelligence”

### 3.1 Visual idea

Use an orbital / connected-systems motif as the visual signature. A central object with carefully controlled orbit lines, reflective surfaces and smaller nodes suggests connected products, systems and ideas. It should feel like a crafted piece of digital art—not a literal planet, stock AI robot or generic circuit-board illustration.

The motif can reappear in restrained ways across:

- Hero artwork.
- Section transitions and divider details.
- AI workflow diagram.
- Small brand marks and loading states.
- Social / presentation graphics, where appropriate.

### 3.2 Hybrid theme logic

The page alternates between two intentional visual environments:

**Light editorial environment**
- Warm near-white canvas.
- Dark ink typography.
- Thin neutral borders.
- Strong negative space.
- Violet/blue accents used sparingly.
- Best suited to brand introduction, capabilities, project cards, company information and contact.

**Dark technology environment**
- Deep navy / charcoal canvas.
- White or cool-grey text.
- Controlled blue, violet and occasional cyan light accents.
- Fine orbital lines and low-intensity glows.
- Best suited to AI / agentic systems and selected technical storytelling.

The contrast should create rhythm, not visual noise. Keep most content on the light canvas; use dark sections as deliberate emphasis.

### 3.3 Overall mood

Premium, modern, precise, calm, inventive and technically confident.

The design should not look like:

- A crypto-token landing page.
- A gaming clan / esports page.
- A generic AI start-up template.
- A portfolio of unrelated gradients and glass cards.
- A corporate stock-photo brochure.

## 5. Homepage: detailed section specification

## 5.1 Header and navigation

**Purpose:** Establish the identity immediately and provide simple routes to the most useful parts of the site.

**Desktop composition**
- Left: CIS symbol + “CYBER INFO SPACE” wordmark.
- Centre/right: compact navigation links.
- Far right: outlined or subtly filled “Start a conversation” CTA with arrow.
- Header sits on the light canvas, with a fine lower border or no border depending on the background.

**Behavior**
- Logo returns to homepage top.
- Navigation links scroll to their sections or open the relevant page.
- CTA scrolls to contact or opens the contact page.
- On scroll, optional sticky header may use a slightly opaque warm-white surface and a restrained backdrop blur. Do not animate its height aggressively.
- Active section indication should be subtle and accessible.

**Mobile composition**
- Logo and wordmark at left.
- Menu button at right, with a clear accessible label.
- Navigation opens as a full-width panel or compact overlay with large touch targets.
- Keep the contact action visible in the open menu.
- Lock background scrolling while the mobile menu is open and return focus correctly when it closes.

**Content**
- Brand name: Cyber Info Space.
- Short label: CIS.
- CTA: Start a conversation.

## 5.2 Hero section

**Purpose:** Explain what CIS does in approximately five seconds and establish a distinctive first impression.

**Recommended copy**

Eyebrow:

> INDEPENDENT TECHNOLOGY ENGINEERING

Headline:

> We build what moves technology forward.

Supporting copy:

> Digital products, intelligent software and autonomous systems—engineered from idea to impact.

Primary CTA:

> Explore our work

Secondary CTA:

> What we build

Optional small supporting line:

> MOBILE · WEB · DESKTOP · AI · OPEN SOURCE

**Desktop layout**
- Two-column composition.
- Text occupies approximately 48–52% of the available hero width.
- Artwork occupies approximately 48–52%, with intentional overlap into open space but never over text.
- Align copy vertically around the centre of the hero artwork.
- Keep the headline to approximately 2–3 lines at the primary desktop width.
- Use one highlighted word or phrase—e.g. “forward.”—in the accent colour.

**Artwork direction**
- A central glossy, dark-blue / violet sphere or abstract core.
- 2–4 thin orbital rings with varied angles and thickness.
- 2–4 smaller satellite nodes.
- Controlled reflections and soft shadows.
- Transparent or warm-white background integration.
- Avoid text inside the artwork; the headline must remain HTML text for accessibility, responsiveness and SEO.

**Mobile layout**
- Eyebrow → headline → paragraph → primary CTA → secondary CTA → artwork.
- Artwork can be smaller and cropped carefully, but the central object must remain visible.
- Do not place text over a busy part of the image.
- Hero should feel complete in the first few mobile scrolls, without forcing the user to read a long intro.

**Interactions**
- Primary CTA scrolls to selected work.
- Secondary CTA scrolls to capabilities.
- Artwork may have a slow, subtle float or orbit effect, but a static image is the default fallback.

## 5.3 Capability strip: “One engineering mindset. Multiple surfaces.”

**Purpose:** Prove breadth quickly and show that CIS can work across multiple product environments.

Heading:

> One engineering mindset. Multiple surfaces.

Use five cards in one desktop row, or a responsive grid. Each card contains a simple line icon, concise title and one or two lines of explanation.

### Capability card content

**01 — Mobile Applications**

> Android, iOS and cross-platform applications built around useful, intuitive experiences.

Examples of scope: native Android, native iOS, cross-platform applications, offline-first utilities, device-level experiences and mobile product engineering.

**02 — Web Platforms**

> Websites, SaaS products and web applications designed to scale with real user needs.

Examples of scope: corporate websites, dashboards, SaaS interfaces, portals, e-commerce experiences, APIs and platform engineering.

**03 — Desktop Software**

> Focused desktop tools for productive, connected and local-first workflows.

Examples of scope: macOS, Windows and cross-platform desktop applications; developer utilities; file and workflow tools; local-first software.

**04 — AI & Agentic Systems**

> AI-powered products, intelligent agents and practical workflow automation.

Examples of scope: LLM-powered features, retrieval-assisted workflows, tool-using agents, task automation, local AI experiments and AI product integration.

**05 — Research & Open Source**

> Developer tools, experiments and reusable engineering ideas shared with the community.

Examples of scope: public repositories, prototypes, technical explorations, documentation and reusable utilities.

**Interaction**
- Cards can link to a capability detail page or relevant work filter.
- Hover state: border accent, subtle elevation and arrow/icon movement of 2–4 px.
- On touch devices, preserve the same content without hover-dependent information.

**Visual treatment**
- Light surface, thin border, moderate corner radius.
- Consistent card height on desktop where practical.
- Icons should be from one coherent line-icon set.
- Do not add a separate gradient or illustration to every card.

## 5.4 AI & agentic systems feature section

**Purpose:** Give AI and agentic engineering a memorable identity while explaining the concept clearly and credibly.

Section label:

> AI-POWERED INNOVATION

Headline:

> Beyond software. Into intelligent systems.

Supporting copy:

> From AI-powered workflows to agentic systems, we build technology that helps people work smarter, solve problems and move ideas forward.

CTA:

> Explore AI & Agentic Systems

**Visual environment**
- Full-width dark navy section.
- Subtle blue/violet light trails or orbital paths.
- Workflow diagram centred on the right or across the lower half.
- Use bright accents only on the workflow nodes and key connection points.

**Workflow diagram**

1. **Observe** — Receive context, input or a task.
2. **Reason** — Interpret the task, select a plan and decide what is needed.
3. **Act** — Use approved tools or perform a defined operation.
4. **Improve** — Evaluate the result, capture feedback and refine the next step.

This is a conceptual communication model, not a claim that every CIS system uses an autonomous learning loop. When describing a real product, document its actual behavior, human approvals, tool permissions and safety boundaries.

**Motion**
- A restrained travelling highlight can move along the workflow path.
- Node glow may pulse gently once when entering the viewport.
- No continuous high-frequency flashing, fast particle fields or distracting background movement.
- Disable non-essential motion when `prefers-reduced-motion: reduce` is active.

**Mobile**
- Stack heading and copy first.
- Place the workflow beneath as a vertical sequence or horizontally scrollable diagram with clear labels.
- Prefer a vertical sequence for accessibility and readability.

## 5.5 Selected work

**Purpose:** Convert broad claims into evidence. This is the most important trust-building section after the hero.

Section label:

> SELECTED WORK

Suggested heading:

> Product engineering across diverse domains.

Supporting copy:

> From consumer apps to developer tools, we turn ideas into useful, reliable digital experiences.

**Layout**
- Desktop: one intro column plus three project cards, or a heading row followed by a three-column grid.
- Tablet: two columns, with the final card aligned naturally.
- Mobile: one column with image / preview above card content.

**Project card anatomy**
1. Project thumbnail or real product screenshot.
2. Project name.
3. One-sentence problem / purpose statement.
4. Category or platform tags.
5. Optional status: Live, Open Source, Prototype or In Development.
6. Link: View project, Live demo or Source code.

**Recommended initial card categories**

- Mobile experiences — use a real app screenshot or a clearly labelled concept preview.
- Connected platforms — use an actual dashboard / web-product screenshot.
- Intelligent tools — use a real developer tool or AI experiment preview.

These are layout categories, not confirmed product names. Replace them with verified CIS projects before publishing. Do not present a concept illustration as a shipped product screenshot.

**Project data model**

Each project should have:

- `name`
- `slug`
- `short_description`
- `problem`
- `solution`
- `platforms[]`
- `technologies[]`
- `category`
- `status`
- `thumbnail`
- `screenshots[]`
- `live_url` (optional)
- `repository_url` (optional)
- `case_study_url` (optional)
- `published_at` (optional)
- `featured` (boolean)

Only show links that exist and have been tested. Omit missing metadata instead of displaying empty labels.

**Project discovery / filtering**
- Provide filter chips only when there are enough real projects to make them useful.
- Search should filter project name, description, category and tags.
- Include a meaningful empty state with a clear reset action.
- If GitHub data is dynamically fetched, show loading, success, empty and error states separately.
- If the API fails, preserve a small curated static project list or offer a direct GitHub link. Do not leave the whole section blank.

## 5.6 Engineering approach

**Purpose:** Explain how CIS thinks and works without fabricating a formal enterprise delivery process.

Suggested heading:

> Thoughtful engineering. Useful outcomes.

Suggested four-step model:

1. **Understand** — Clarify the problem, users, constraints and desired outcome.
2. **Design** — Define the experience, system shape and practical scope.
3. **Build** — Implement, integrate and test the product in focused increments.
4. **Refine** — Learn from usage, fix weaknesses and improve the experience.

Keep the explanation concise. Use a horizontal four-step process on desktop and a vertical list on mobile. Link each step to detailed process material only if that material exists.

> Explore GitHub

Secondary CTA, when relevant:

## 6. Visual design system

The values below are recommended starting tokens. They should be refined in the final design file and checked in the browser at real viewport sizes.

### 6.1 Colour palette

| Token | Suggested value | Usage |
|---|---:|---|
| `ink-950` | `#101426` | Main headline / dark section text |
| `navy-950` | `#080D22` | Dark feature section and footer |
| `navy-900` | `#101A37` | Dark cards and layered surfaces |
| `paper-50` | `#FAF9F6` | Primary light page background |
| `paper-100` | `#F3F2EF` | Alternate light section |
| `white` | `#FFFFFF` | Cards and high-contrast surfaces |
| `slate-500` | `#687086` | Secondary text |
| `line-200` | `#E4E5EB` | Light borders and dividers |
| `violet-600` | `#5544F5` | Main accent / primary CTA |
| `blue-500` | `#477BFF` | Secondary accent and links |
| `cyan-300` | `#65DDF4` | Rare dark-section highlight |
| `success-500` | `#159A72` | Confirmed success states only |

**Colour rules**
- Violet is the primary brand accent; blue is supportive.
- Cyan is reserved for small highlights in the dark AI section.
- Do not use a gradient on every button, heading and card.
- Ensure all text / background combinations meet WCAG AA contrast at minimum.
- Never communicate status using colour alone.

### 6.2 Typography

Recommended direction: a contemporary geometric / neo-grotesk sans serif with strong headline weights and highly readable body text.

Suggested font stack:

- Primary: `Inter`, `Geist`, or another licensed / properly bundled contemporary sans-serif.
- System fallback: `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`.
- Monospace accent: system monospace for code, metadata and technical labels.

Do not load several font families or many weights. Use a small, intentional set: regular, medium, semibold and bold.

**Responsive type scale (starting point)**

| Role | Desktop | Mobile | Weight / note |
|---|---:|---:|---|
| Display / hero | 64–76 px | 40–48 px | Bold; tight line-height |
| H1 | 52–64 px | 38–44 px | Bold |
| H2 | 40–48 px | 30–36 px | Semibold / bold |
| H3 | 24–30 px | 22–26 px | Semibold |
| Card title | 18–20 px | 17–19 px | Semibold |
| Body large | 18–20 px | 17–18 px | Regular |
| Body | 16–18 px | 16 px | Regular |
| Metadata | 12–14 px | 12–13 px | Medium, letter-spaced sparingly |

Use fluid sizing with `clamp()` where appropriate. Keep body copy comfortable and avoid long line lengths.

### 6.3 Layout and spacing

- Maximum content width: approximately 1,200–1,320 px.
- Desktop side gutters: 48–72 px, adapting to viewport width.
- Tablet gutters: 28–40 px.
- Mobile gutters: 20–24 px.
- Main section spacing: 88–128 px desktop; 64–88 px mobile.
- Card gap: 16–24 px.
- Text measure: approximately 55–70 characters for long-form paragraphs.
- Use a 4 px base spacing rhythm, with commonly used increments of 8, 12, 16, 24, 32, 48, 64 and 96 px.

### 6.4 Grid

- Desktop: 12-column layout.
- Tablet: 8-column layout.
- Mobile: 4-column layout.
- Capability cards: five columns only on sufficiently wide desktop; 2–3 columns on medium viewports; one column or a carefully designed two-column grid on narrow mobile.
- Project cards: 3 columns desktop, 2 tablet, 1 mobile.

### 6.5 Shape, borders and depth

- Cards: 12–18 px corner radius.
- Buttons: 10–14 px corner radius; avoid excessive pill shapes except small tags.
- Large artwork / hero containers: 20–28 px radius only if a container is visually needed.
- Light borders: 1 px neutral line.
- Shadows: diffuse and low contrast; avoid dark, heavy drop shadows on every component.
- Dark section: use layered navy surfaces and localised glow rather than a large generic gradient wash.

### 6.6 Icons

- Use one consistent outline icon family.
- Stroke weight should remain visually consistent.
- Icons should support the label, not replace it.
- Avoid mixing emoji, filled icons, outline icons and 3D icons in the same capability row.

### 6.7 Imagery and product screenshots

**Priority order**
1. Actual screenshots of shipped CIS products.
2. Actual screenshots of working prototypes, labelled as prototypes.
3. Purpose-made conceptual artwork, clearly not represented as a shipped product.
4. Carefully selected abstract supporting imagery.

For project cards, use product screenshots rather than generic stock technology art whenever possible. Keep a consistent image ratio (approximately 16:10 or 16:9) and crop deliberately.

**Image treatment**
- Rounded corners consistent with the card system.
- Light neutral or dark backing surfaces depending on the product screenshot.
- Avoid adding fake UI labels or unreadable microcopy into generated mockups.
- Provide accurate alternative text for meaningful images. Decorative artwork should use empty alt text.

## 7. Responsive behavior specification

The design must be responsive by composition, not merely by shrinking widths.

### 7.1 Breakpoint guidance

| Range | Layout intent |
|---|---|
| `>= 1440 px` | Wide desktop; generous whitespace; cap content width |
| `1200–1439 px` | Standard desktop; maintain two-column hero |
| `900–1199 px` | Compact desktop / landscape tablet; tighter gutters and flexible grids |
| `640–899 px` | Tablet; navigation may collapse; grids become two columns |
| `< 640 px` | Mobile; single-column content and compact navigation |

These are design breakpoints, not mandatory device categories. Components should respond to their available width.

### 7.2 Desktop

- Full horizontal navigation.
- Two-column hero with large artwork.
- Capability cards in one row when width allows.
- Wide dark AI feature section with diagram.
- Three-column projects.
- Four-step process in a horizontal row.

### 7.3 Tablet

- Navigation may shorten or collapse before labels collide.
- Hero can move to a 55/45 or stacked composition depending on width.
- Capability cards wrap naturally; preserve equal visual weight.
- AI diagram may move beneath its copy.
- Project grid becomes two columns.

### 7.4 Mobile

- Compact header with menu control.
- Hero copy before artwork.
- Headline no wider than the content column; avoid awkward one-word orphan lines.
- CTAs stack or wrap with full-size touch areas.
- Capability cards stack or use a clear two-column grid only if each card remains readable.
- AI workflow becomes a vertical process.
- Projects stack vertically with readable summaries and clear action links.
- Footer becomes a simple stacked layout.
- No horizontal page overflow.

### 7.5 Touch and input behavior

- Minimum touch target: 44 × 44 CSS px where practical.
- Do not depend on hover to reveal a link, label or project description.
- Ensure focus and active states remain visible on touch and keyboard input.
- Make controls sufficiently separated to prevent accidental taps.

## 8. Motion and interaction principles

Motion should make the experience feel considered—not busy.

### 8.1 Motion language

- Short, soft transitions.
- Gentle easing with no exaggerated bounce.
- Small distance changes for hover and reveal animations.
- One signature movement: a very slow orbit / drift in the hero artwork, only when performance and reduced-motion preferences allow.

### 8.2 Suggested timings

| Interaction | Duration | Behavior |
|---|---:|---|
| Button hover / press | 140–200 ms | Colour, border and 1–2 px movement |
| Card hover | 180–240 ms | Small lift, border accent, arrow movement |
| Menu open / close | 180–260 ms | Fade + short slide |
| Section reveal | 350–550 ms | Fade + 12–20 px translate |
| Hero decorative drift | 8–20 s loop | Very slow and subtle; optional |

### 8.3 Motion safeguards

- Respect `prefers-reduced-motion`.
- Keep essential content visible if animation never runs.
- Do not animate large layout dimensions on scroll.
- Avoid scroll-jacking, forced horizontal scroll sections and cursor-following effects.
- Avoid flashing, intense parallax and infinite particle animations.
- Lazy-load non-critical media and avoid starting multiple heavy animations simultaneously.

## 10. Trust and credibility requirements

A premium appearance is not enough. The content must earn trust.

### 10.1 Evidence hierarchy

Use proof in this order:

1. Working product or live demo.
2. Actual screenshots and a clear explanation of the problem solved.
3. Public source repository or documentation.
4. Technical case study describing architecture, decisions and trade-offs.
5. Verifiable testimonials, clients or outcomes, only with permission and evidence.

### 10.2 Claims that require verification

Do not publish without confirmation:

- Number of clients, employees, projects or users.
- Years of operation or experience.
- Revenue, growth or performance improvements.
- Security, compliance or certification claims.
- “Enterprise-grade”, “production-ready” or “mission-critical” claims.
- Client names, logos, testimonials or partner endorsements.
- Claims of fully autonomous agents or guaranteed AI accuracy.

### 10.3 Project status labels

Use consistent labels:

- **Live** — publicly usable and working.
- **Open Source** — source repository is public and accessible.
- **Prototype** — working proof of concept, not a production release.
- **In Development** — actively being built; no release promise implied.
- **Archived** — no longer actively maintained.

Do not use “Live” for a concept mockup or untested demo.

## 11. Accessibility and usability requirements

Target: **WCAG 2.2 AA** as a practical design and implementation goal.

- Semantic landmarks: `header`, `nav`, `main`, `section`, `footer`.
- Exactly one descriptive H1 on the homepage.
- Logical heading hierarchy; do not choose heading tags only for visual size.
- Full keyboard access to navigation, menus, filters, cards and forms.
- Visible focus indicators with adequate contrast.
- Skip-to-content link.
- Meaningful link labels; avoid repeated ambiguous “Read more” links without context.
- Form fields with persistent labels and clear error messages.
- Descriptive accessible names for icon-only controls.
- Text contrast at least 4.5:1 for normal text and 3:1 for large text / relevant UI elements.
- Do not place essential text inside images.
- Respect reduced-motion preferences.
- Ensure zoom to 200% does not hide content or break essential interactions.
- Check screen-reader order after responsive layout changes.
- Do not use colour alone to indicate active filters, error states or status.

## 12. Performance and technical design considerations

This is a design handoff, not a mandated frontend stack. The implementation should preserve the existing GitHub Pages / static-hosting advantage unless there is a clear reason to introduce server infrastructure.

### 12.1 Performance goals

Aim for strong Core Web Vitals on representative mobile devices and realistic network conditions. Suggested field targets:

- LCP: 2.5 seconds or better.
- INP: 200 ms or better.
- CLS: 0.1 or lower.

These are targets to measure, not results already achieved.

### 12.2 Asset strategy

- Use AVIF or WebP for large raster imagery where supported, with suitable fallback.
- Provide responsive image sizes using `srcset` / `sizes`.
- Set explicit width and height or aspect ratio to reduce layout shift.
- Use SVG for simple logos and icons.
- Compress hero artwork carefully; it is visually important but should not dominate page weight.
- Lazy-load below-the-fold images.
- Do not lazy-load the primary hero image if it is the likely LCP element.
- Prefer CSS effects over heavy JavaScript animation libraries when possible.

### 12.3 Static hosting compatibility

For a GitHub Pages deployment:

- Use static HTML/CSS/JS or a static-site build that exports deployable files.
- Confirm correct base path and asset paths for the repository's Pages URL.
- Avoid server-only features unless a separate service is introduced.
- Keep contact-form processing on a verified form provider or backend endpoint; static hosting alone does not process form submissions.
- Make project data available as static JSON / curated content where possible.
- If using the GitHub API in the browser, handle rate limits, network errors and missing metadata gracefully. Never expose a private token in client-side code.

### 12.4 Technology-neutral implementation structure

Suggested separation:

- `content/` — project and capability data.
- `components/` — navigation, buttons, cards, tags, footer and reusable UI.
- `sections/` — homepage sections.
- `styles/` — tokens, typography, layout and component styles.
- `assets/` — logos, project screenshots and artwork.
- `scripts/` — small interactions, filters and enhancement logic.

The design should not depend on a particular framework. If a component framework is chosen later, retain the same content model and visual tokens.

## 15. Required states and edge cases

Design and test these states before launch:

### Project section
- Projects loaded.
- No projects configured.
- Search with results.
- Search with no results.
- API request loading.
- API request failed.
- One project only.
- Long project name / long description.
- Missing screenshot.
- Missing live URL or repository URL.

### Navigation
- Menu closed.
- Menu open.
- Escape key closes menu.
- Navigation item selected.
- Focus remains inside the open menu where appropriate.
- Focus returns to menu trigger after close.

### Contact
- Invalid email.
- Required field missing.
- Submission in progress.
- Submission confirmed.
- Submission failed.
- User can recover from an error without losing all entered data.

### Responsive
- 320 px narrow viewport.
- 360–390 px common mobile widths.
- 768 px tablet.
- 1024 px compact laptop.
- 1440 px desktop.
- 1920 px wide desktop.
- Browser zoom at 200%.

## 17. Acceptance criteria

The redesign is ready for handoff / implementation review when:

1. A first-time visitor can understand what Cyber Info Space does within five seconds.
2. The five capability areas are visible and understandable without specialist knowledge.
3. The website feels premium, coherent and distinctive without relying on fabricated scale or credibility claims.
4. Real work and open-source activity can be discovered in one or two actions.
5. AI and agentic systems are explained in plain language and do not overstate autonomy or reliability.
6. The homepage has a complete desktop, tablet and mobile layout.
7. All navigation, CTAs, cards, filters and forms have documented interaction states.
8. The site remains usable with keyboard navigation and reduced-motion settings.
9. There are graceful loading, empty and error states for dynamic project data.
10. All visible links, images, metadata and contact routes are verified before launch.
11. The implementation meets agreed performance and accessibility checks.
12. No placeholder project, testimonial, logo, metric or claim is accidentally published as fact.

- Publish only verified project and company information.
- Review analytics / user feedback if enabled.
- Improve the project directory as more work becomes ready to showcase.
- Add case studies only when there is enough evidence and detail to make them valuable.

## 19. Final creative guardrails

**Do**
- Make the product work the strongest proof of capability.
- Use whitespace and typography to create confidence.
- Use violet / blue accents with restraint.
- Make the dark AI section a clear visual moment.
- Keep the mobile experience intentional and highly readable.
- Give open source a visible place in the brand story.
- Use plain language to explain complex engineering.

**Do not**
- Invent customers, metrics, awards, staff or company history.
- Label a concept as a live product.
- Fill every section with gradients, glassmorphism or animated particles.
- Put critical text inside images.
- hide project or contact links behind decorative interactions.
- Make the homepage a long list of technologies without explaining outcomes.
- Depend on a live GitHub API call as the only way to show the portfolio.
